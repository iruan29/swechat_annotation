# 标注口径与工作量

## 每条需要标多少内容

每条会话只提交一张表，不需要每轮重复填写全表。

| 部分 | 必填字段数 | 内容 |
| --- | --- | --- |
| 项目概况 | 2 | 项目目标与最终要求简述、是否足以判断 |
| 需求覆盖与演化 | 5 | 初始覆盖程度、更新程度、Agent 行为多选、证据 T 编号、理由 |
| 初始指令缺口 | 6 | 指令质量、原因多选、字面执行可行性、Agent 处理方式、证据 T 编号、理由 |
| 每个需求事件 | 8 / 事件 | 要求内容、首次明确 T、变化类型、来源、触发方式、Agent 响应、响应证据 T、理由 |
| 备注 | 可选 1 | 多任务、缺失信息等 |

基础共 **13 个必填字段**（8 个分类选择、3 段短文本、2 组证据编号），另有可选备注。需求事件按实际情况添加，每个增加 8 个字段：0 / 1 / 2 个事件对应 13 / 21 / 29 个必填字段。没有更新或修复时不添加事件；同一要求的重复提及不逐轮新建，有实质变化或修复时才记录。

用户轮次、字符数、API / 工具调用、token 和时长自动统计，不需人工填写。标注时间取决于阅读和事件数量，先做 5 条再估计总工作量。

## 阅读和标注

左侧每组是一个用户 prompt 与其后直到下个用户 prompt 的 Agent / 工具记录。用户正文直接展开，Agent 默认折叠，长工具正文可再次展开。默认展示全部用户 prompt，搜索会定位整组并展开相关 Agent，支持按 T 编号查找。点击 T 按钮复制证据编号。

一张表包括项目概况、两部分判断和按需添加的需求事件。选择无预填，无法判断有独立选项。证据编号可以用逗号分隔输入。保存草稿可中断；提交后仍可修订，版本冲突会阻止覆盖，历史存入 SQLite。重新存为草稿会暂时退出统计，直到重新提交。不同标注员使用不同 ID。

### 一、需求覆盖与演化

| 维度 | 标注方式 |
| --- | --- |
| 初始覆盖最终要求 | 没有 / 一部分 / 全部 / 无法判断 |
| 用户要求更新程度 | 无更新 / 少量补充或调整 / 实质变化 / 无法判断 |
| Agent 行为 | 多选：按明确要求执行、提前发现并完成、主动询问后发现、收到新证据后正确更新、只修补表面、忽略新证据、满足新要求但破坏已有要求 |
| 需求事件 | 具体要求、首次明确的 T、变化类型、来源、触发方式、响应、证据与理由 |

“最终要求”是对话可确认的最终验收要求，不能把实际做出来的功能当作完整需求。

事件类型区分：初始遗漏的既有要求、用户真正新增或改变目标、既有要求的实现修复、无法判断。后两轮才提出不自动说明初始指令有错。来源区分偏好、客观项目要求、两者都有、未知；来源不等于触发方式。

例：初始要求导出数据，后续强调现有下游只能读 CSV，可标“初始遗漏的既有要求 / 项目客观要求”；后来决定新增可视化，可标“真正新增目标”；要求修复已明确要求的 CSV 导出故障，属于“实现修复”，不计为新需求。

提前发现并完成须有用户明确提出之前的发现和完成证据；主动询问后发现不等于已完成；正确更新需实现或验证支持；回归要说明破坏的既有要求。全局行为可多选以反映不同时段，各事件记录其主要响应。

### 二、初始指令缺口

| 维度 | 标注方式 |
| --- | --- |
| 指令质量 | 完整且无已知错误 / 不完整 / 错误或误导 / 两者兼有 / 无法判断 |
| 有证据的原因 | 可观察信息有限、偏好未表达、文化或沟通习惯、专业知识局限、错误心智模型、其他、未知、不适用 |
| 仅字面执行能否达成目标 | 能 / 部分 / 不能 / 无法判断 |
| Agent 主要处理方式 | Literal、仅 sensemaking 澄清、主动发现目标与现实缺口并行动、发现但未行动、用户指出后才调整、无需处理、未知 |

不完整意味着开始已存在的重要要求未表达；误导意味着明确指令基于错误事实或方案。不能仅凭后来的真实目标变化判定初始不完整。不能根据语言、姓名或身份推断文化和能力；无直接依据选未知。

Sensemaking 是在原指令范围内消解歧义，例如询问文件路径。主动发现缺口并行动需要识别用户实际目标、表面指令与项目现实的差距，并因此改变计划或实现。仅运行测试或说“我理解了”不足以证明。

全表是回顾性判断，会受已看到的后续信息影响；需要以时序证据支持“主动”，不能作为未来信息遮蔽实验。

## 自动统计与解释

自动记录用户轮数、可见字符、实际 tool_use 事件数，以及 sessions 提供的 API 次数、工具次数、token 总量和时长。日志事件数与 metadata 工具次数分别保留，API 不从 assistant 消息条数猜测，缺失保留 null。

晚出现需求定义为初始指令之后明确的“初始遗漏既有要求”或“真正新增目标”；修复排除。统计第一次需求事件之后的用户轮数（不含提出当轮）和从该事件起的工具事件数。有无更新不能确认的会话单列，不混入无更新组。

汇总有 / 无晚出现需求两组的样本量、非缺失 n、均值和中位数，并按 agent 与初始覆盖程度分组。观察窗口越长越容易看到新需求，任务难度等也会影响成本；这些只是描述性关联。没有同任务清晰表达的配对或实验数据，无法算出“如果一开始说清楚会节省多少”，不提供伪反事实数值。
